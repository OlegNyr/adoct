= Задача: выгружать только реально используемые вложения
:toc: macro
:toclevels: 2

toc::[]

== Зачем

Сейчас при экспорте страницы качаются *все* вложения, которые вернул Confluence, а не только те,
на которые ссылается тело страницы. На большом пространстве это основной источник лишнего трафика
и времени выгрузки.

Усугубляется тем, что карта вложений берётся из `/content/{id}/descendant/attachment`
(`ConfluenceClient.java:227`) — то есть для каждой страницы возвращаются вложения *всего её
поддерева*. В итоге вложение с листа на глубине N скачивается N+1 раз — в папку `attache/`
каждого предка.

Цель: настройка, при которой в `attache/` попадают только файлы, на которые есть ссылка в
storage-теле страницы.

NOTE: Формат заметок — под каждым пунктом блок `КОММЕНТАРИЙ:`. Пишите туда решение / правки /
«не делаем».

Доработано после код-ревью (см. `doc/task-performance.adoc`): имена картинок из `<img src>`
декодируются из percent-encoding (иначе файл не находился), и при включённом фильтре `attache/`
очищается перед загрузкой — без этого фильтр лишь запрещал новые загрузки, а вложения от прошлых
прогонов оставались лежать.

CAUTION: На живом Confluence не проверялось. Главный остаточный риск — расхождение имени в storage
с именем вложения (регистр, неразрывные пробелы): тогда файл не скачается, а ссылка в `.adoc`
останется. При выключенном флаге поведение прежнее, откат — галочкой.

== Ядро: определить «используемые» вложения

=== 1. Метод `usedAttachments()` в `ConvertStorageToAdoc`

Собрать множество имён файлов, на которые реально ссылается storage-тело страницы.
Единая точка входа, которой пользуется `DispatcherPage`.

КОММЕНТАРИЙ:

=== 2. Источник A — картинки `<ac:image><ri:attachment ri:filename>`

Уже реализовано в `ConvertStorageToAdoc.imageAttachments()` (`ConvertStorageToAdoc.java:147`).
Переиспользовать, не дублировать.

КОММЕНТАРИЙ:

=== 3. Источник B — ссылки `<ac:link><ri:attachment ri:filename>`

Уже разбирается в `ConvertStorageToAdoc.getLinks()` (`ConvertStorageToAdoc.java:125-128`) и
превращается в `LinksAttachment`. Вытащить оттуда имена файлов.

КОММЕНТАРИЙ:

=== 4. Источник C — макросы `drawio` / `inc-drawio`

Параметр макроса — `diagramName` (`DrawioMacro.java:26`).

CAUTION: `DrawioRenderer.prepareEditable` (`DrawioRenderer.java:75-119`) ищет на диске *пять*
разных файлов:
`<name>`, `<name>.png`, `<name>.svg`, `<name>.drawio.png`, `<name>.drawio.svg`.
В набор «используемых» надо класть все пять кандидатов, иначе диаграммы перестанут собираться.

КОММЕНТАРИЙ:

=== 5. Ревизия остальных макросов

Пройтись по макросам, которые могут ссылаться на вложения: `view-file`, `viewpdf`, `multimedia`,
`gallery`, `attachments`, `include`, `swagger`. Решить, какие учитывать.
Часть из них сейчас в `IgnoreOkMacro` (`IgnoreOkMacro.java:26`) и в вывод вообще не идёт —
для таких вложение не нужно.

КОММЕНТАРИЙ:

=== 6. Политика для нераспознанного контента

Неизвестный макрос `MacroBuilder` дропает — значит его вложение не попадёт в набор и не скачается.
Решить: нужен ли «мягкий» режим (при встрече неизвестного макроса качать всё) или достаточно
`WARN` в лог.

КОММЕНТАРИЙ:

== Фильтрация при выгрузке

=== 7. Применить фильтр в `DispatcherPage.export`

`DispatcherPage.java:260-267` — отфильтровать `mainPage.attachment().values()` по набору из п.1
перед вызовом `client.loadAttach(...)`.

КОММЕНТАРИЙ:

=== 8. Коллизии имён из-за `descendant/attachment`

`mainPage.attachment()` — это `Map<имя файла, LinkResult>` по вложениям *всего поддерева*.
При фильтрации по имени файл с таким же именем с чужой страницы может подменить нужный.

Решить: чинить эндпоинт на `/content/{id}/child/attachment?limit=200` в рамках этой задачи или
выносить отдельно.

КОММЕНТАРИЙ:

=== 9. Не отсечь `foreignImages`

`DispatcherPage.foreignImages` (`DispatcherPage.java:329-344`) добирает картинки, лежащие на
*другой* странице (`<ri:attachment><ri:page/></ri:attachment>`). Они по определению используемые —
фильтр к ним применять не нужно. Проверить, что не отсекутся.

КОММЕНТАРИЙ:

=== 10. Порядок вычислений

`converter` создаётся на `DispatcherPage.java:246`, `loadAttach` — на `:263`, `converter.convert()`
— на `:313`. Набор считается по тому же распарсенному документу, лишнего парсинга быть не должно.

КОММЕНТАРИЙ:
