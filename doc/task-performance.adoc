= Задача: производительность выгрузки пространства
:toc: macro
:toclevels: 2

toc::[]

== Проблема

Выгрузка большого пространства занимает ~20 минут только на «предобработке», до того как будет
записана первая страница. Прогресс-бар при этом молчит — выглядит как зависание.

Корневая причина одна: *количество последовательных HTTP-запросов, каждый из которых поднимает
новое TLS-соединение*. Парсинг (Jsoup, AST, writer) в этой картине пренебрежимо дёшев.

=== Грубая модель

Для пространства на ~1500 страниц и ~3000 вложений, при RTT+TLS ≈ 400 мс на запрос без
переиспользования соединения:

[cols="3,1,1", options="header"]
|===
| Что | Запросов | Время

| `buildSiteMap`: `childPages` на каждую страницу | ~1500 | ~10 мин
| `getMainPage` корней: `/descendant/attachment` пачками по 25 | ~120 | ~1 мин
| `labels(id)` на каждую страницу | ~1500 | ~10 мин
| `childPages` повторно в `export` | ~1500 | ~10 мин
|===

NOTE: Формат заметок — под каждым пунктом блок `КОММЕНТАРИЙ:`. Пишите туда решение / правки /
«не делаем».

== Этап 1 — соединения и пред-проход

Самая большая отдача при наименьшем риске. Ожидаемый эффект: пред-проход с ~20 минут до десятков
секунд.

=== 1. Переиспользовать один `CloseableHttpClient`

Сейчас *каждый* запрос собирает новый клиент внутри try-with-resources:

[source,java]
----
// ConfluenceClient.java:278, :259, :60
try (var client = httpClientBuilder.build()) {   // новый пул, новый SSL-контекст, новый handshake
    return client.execute(...);
}
----

Connection pooling и keep-alive не работают вообще. На HTTPS это ~100–300 мс постоянных накладных
на каждый запрос.

Что делать: собрать клиент один раз в конструкторе с `PoolingHttpClientConnectionManager`
(`maxTotal`/`maxPerRoute` ≈ 32), реализовать `Closeable`, закрывать по завершении выгрузки.
Правка в трёх методах: `doRequestAndFailIfNot20x`, `downLoad`, `verifyToken`.

Отдельно проверить: кто владеет жизненным циклом `ConfluenceClient` в
`ConvertDocsUrlToAdoc.java:44`, в MCP-тулах и в Maven-плагине — клиент теперь надо закрывать.

КОММЕНТАРИЙ:

=== 2. Убрать рекурсию из `buildSiteMap`

`DispatcherPage.java:124-152`. Чтобы построить карту `заголовок → папка` для кросс-ссылок,
`walkSiteMap` рекурсивно обходит всё дерево, делая `client.childPages(id)` на *каждую* страницу.
Это и есть основные 20 минут.

Что делать: забрать всё дерево пространства одним пагинированным запросом:

----
GET /rest/api/space/{key}/content/page?limit=100&start=N&expand=ancestors,version
----

Из `ancestors` восстанавливается полный путь папок для каждой страницы.
1500 страниц → *~15 запросов вместо 1500*.

TIP: Эндпоинт уже используется в `ConfluenceClient.spaceRootPages` (`ConfluenceClient.java:161`),
только с `depth=root`, и пагинация уже написана в `pagedRefs` (`:167`) — то есть путь проверенный.

Для выгрузки поддерева (`generate(pageId)`, а не `generateSpace`) — то же самое через
`/rest/api/content/search?cql=ancestor=<id> and type=page&expand=ancestors,version`.
Нужен фолбэк на текущий рекурсивный обход, если CQL недоступен или упёрся в лимит выдачи.

КОММЕНТАРИЙ:

=== 3. Переиспользовать дерево в `export`

`DispatcherPage.java:236` заново дёргает `client.childPages(id)` для каждой страницы, хотя после
п.2 полное дерево уже в памяти. Брать детей из карты. Минус ещё ~1500 запросов.

КОММЕНТАРИЙ:

=== 4. Прогресс на пред-проходе

`buildSiteMap` не дёргает `progressCallback` ни разу — отсюда ощущение зависания. Добавить
сообщения хотя бы по страницам пагинации.

== Этап 2 — трафик вложений

Убирает кратное дублирование скачивания.

=== 5. `descendant/attachment` → `child/attachment`

`ConfluenceClient.java:227` использует `/content/{id}/descendant/attachment`, причём *без параметра
`limit`* (дефолт 25).

Два следствия:

* для корневой страницы это все вложения пространства → сотни страниц пагинации, и так для *каждой*
  страницы дерева;
* `DispatcherPage.java:260-267` качает всю эту карту в `attache/` текущей страницы, поэтому
  вложение с листа на глубине N скачивается N+1 раз — в папку каждого предка. Объём загрузки
  ≈ (объём вложений) × (средняя глубина).

Заодно это баг: в `attache/` корня лежат тысячи чужих файлов.

Что делать: `/content/{id}/child/attachment?limit=200`.

IMPORTANT: Пересекается с `doc/task-used-attachments.adoc` п.8 — решить, в какой из двух задач это
делается, чтобы не разъехалось.

КОММЕНТАРИЙ:

=== 6. `loadAttach` не пропускает уже скачанное

[source,java]
----
// ConfluenceClient.java:438-441
if (Files.exists(file)) {
    log.warn("Ignore load {} file exist", file);   // пишет "ignore", но не continue
}
byte[] bytes = downLoad(value.url());              // качает всё равно
----

Инкрементальная перевыгрузка качает все вложения заново. Добавить `continue`.

Решить попутно: нужен ли принудительный перекач (флаг), если вложение изменилось на сервере —
по имени файла это не видно.

КОММЕНТАРИЙ:

=== 7. Свернуть `labels` в основной запрос

`ConfluenceClient.java:199` — отдельный `GET /content/{id}/label` на каждую страницу.
Добавить `metadata.labels` в `expand` у `getMainPage` (`:82`) и брать оттуда. Минус ~1500 запросов.

КОММЕНТАРИЙ:

== Этап 3 — инкрементальная выгрузка

=== 8. Проверять версию до загрузки тела

`DispatcherPage.java:239` вызывает `isUnchanged` уже *после* `getMainPage`, то есть после
скачивания `body.storage` + `body.view` + всех вложений. Инкремент не экономит ни трафик, ни время.

Что делать: в дереве из п.2 уже есть `version.when` (`expand=version`). Сравнивать с версией из
локального `index.<ext>` (`isUnchanged`, `:389-400`) и грузить тело только для изменившихся страниц.

Эффект: повторная выгрузка большого пространства = ~15 запросов + только изменившиеся страницы.

Проверить: чтение локального `index.<ext>` для 1500 страниц — это 1500 обращений к диску.
Возможно, стоит вести отдельный файл-манифест версий в корне выгрузки.

КОММЕНТАРИЙ:

== Этап 4 — параллелизм и кэши

Самое рискованное, делать последним и только после этапов 1–3.

=== 9. Кэш резолва ссылок на весь прогон

`DispatcherPage.java:454` (`client.user`) и `:488` (`client.search`) вызываются без кэша между
страницами. Одни и те же пользователи резолвятся сотни раз.

Добавить `Map<userKey, LinkResult>` и `Map<title+space, LinkResult>` на время выгрузки.
Отрицательный результат (не нашли) тоже кэшировать, иначе каскад `title =` → `title ~` повторится.

КОММЕНТАРИЙ:

=== 10. Параллельное скачивание вложений

`ConfluenceClient.loadAttach` (`:436`) — цикл по файлам. Файлы независимы, распараллеливается
безопасно (пул 4–8 или виртуальные потоки). Требует п.1, иначе упрёмся в хендшейки.

КОММЕНТАРИЙ:

=== 11. Параллельная выгрузка страниц

Требует привести в порядок общее изменяемое состояние `DispatcherPage`:

* `pageFolders`, `pageIdFolders`, `prefetched` — обычные `HashMap`;
* поле `destination` (`:75`) перезаписывается на каждой странице, используется для баг-репорта;
* `progressCallback` уходит в IDE-`ProgressIndicator` — проверить потокобезопасность и как считать
  `fraction` при параллельном обходе.

КОММЕНТАРИЙ:

=== 12. Парсинг `view` дважды на страницу

`ConvertStorageToAdoc.java:88` (`resolveLink`) и `:168` (`imageSources`) отдельно вызывают
`Jsoup.parse(view)`. `view` — самое тяжёлое тело в ответе. Парсить один раз, лениво, и переиспользовать.

CPU, не сеть — эффект заметно меньше пунктов выше. Делать, если после этапов 1–3 упрёмся в процессор.

КОММЕНТАРИЙ:

=== 13. Не запрашивать `body.view`, когда он не нужен

`getMainPage` всегда тянет `body.view` (`ConfluenceClient.java:82`) — это заметная доля трафика.
Проверить, во всех ли сценариях он реально нужен (используется для резолва ссылок и
`foreignImages`), и можно ли не запрашивать его при выключенных `crossPageLinks` /
`includeAttachments`.

== Порядок и ожидаемый эффект

[cols="1,3,1,1", options="header"]
|===
| Этап | Содержание | Риск | Ожидаемый эффект

| 1 | пул соединений, дерево одним запросом, прогресс | низкий | пред-проход: ~20 мин → десятки секунд
| 2 | вложения: child вместо descendant, дедуп, labels в expand | средний | объём загрузки в разы меньше
| 3 | версия до загрузки тела | средний | повторный прогон почти бесплатный
| 4 | кэши, параллелизм, парсинг | высокий | утилизация канала
|===

Этапы 1 и 2 покрываются существующими тестами с фейковым `ConfluenceGateway`
(`DispatcherPageTest`, `DispatcherPageIntegrationTest`, `ConfluenceClientTest`) — но фейк придётся
расширить под новый способ получения дерева.
